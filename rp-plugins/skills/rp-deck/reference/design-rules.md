# rp-deck 디자인·전달력 규칙 (생성 SSOT)

장표 HTML을 생성할 때 반드시 따른다. 근거는 출처 표기.
비주얼 토큰·컴포넌트 마크업은 [`template.html`](template.html)이 SSOT — 클래스·CSS를 그대로 재사용하고 내용만 채운다.
주제별로 **무엇을 어떤 그림으로 그릴지**는 [`visual-patterns.md`](visual-patterns.md)가 SSOT.

## 0. 독자 기준 (모든 규칙의 전제)

**독자는 그 기술을 처음 듣는 사람이다.** 개발자만이 아니라 기획자·디자이너·비전공 대학 4학년이 읽어도 이해되게 쓴다.

| 규칙 | 내용 |
|------|------|
| 사전지식 0 가정 | "다들 알겠지만"에 해당하는 개념도 설명한다. 아는 사람은 넘기면 되지만, 모르는 사람은 여기서 멈춘다 |
| 첫 등장 = 그 자리에서 풀기 | 용어·도구·약어가 처음 나오면 그 슬라이드에서 뜻을 준다(각주 또는 소개 장). 뒤로 미루지 않는다 |
| 쉬운 말 먼저, 정확한 말 다음 | 일상 비유·쉬운 표현으로 감을 준 뒤 정식 용어를 붙인다. `.plain` 박스를 활용한다 |
| "왜"가 "어떻게"보다 앞 | 동작·구조를 설명하기 전에 "이게 없으면 뭐가 불편한지"를 먼저 한 장 둔다 |
| 결과만 말하지 않기 | "성능이 좋아요"로 끝내지 말고 무엇이 어떻게 좋아지는지 수치·장면으로 보여준다 |
| 분량보다 이해 | 이해에 필요하면 장을 늘린다. 어려워서 짧은 것보다 쉬워서 긴 편이 낫다(§9) |
| **가장 어려운 장엔 풀이 필수** | 덱에서 개념 도약이 가장 큰 장을 하나 고른다. 그 장에는 `.plain`을 **반드시** 붙인다. 어려운 장일수록 빠뜨리기 쉽다 |

**자가 점검**: 이 덱을 그 기술을 모르는 기획자가 혼자 읽는다고 상상한다. 멈칫할 지점이 있으면 그 자리에 설명·비유·각주를 더한다.

## 1. 덱 구조 (전달 순서)

| 규칙 | 내용 | 근거 |
|------|------|------|
| 결론 먼저 | 각 섹션은 결론→근거 순. 빌드업 금지 | Minto Pyramid |
| SCQA 오프닝 | 표지 다음 도입부: 상황→문제→질문→답(권고) | Minto/SCQA |
| 피라미드 그룹핑 | 하위 근거는 상위 메시지로 수렴 (MECE) | Minto |
| 메시지 기반 | 목차·섹션은 주제 라벨이 아니라 주장으로 | Assertion-Evidence |
| 내러티브 | 데이터 나열이 아니라 긴장→해소의 흐름 | Duarte |

표준 흐름: 표지 → 목차(주장형) → [섹션구분 → 큰숫자/카드/대비/표/차트/다이어그램/단계/코드/공식] 반복 → 마무리 한 줄.

컴포넌트(마크업은 [`template.html`](template.html)): 표지·목차·섹션구분·큰숫자(KPI)·요약카드·2단대비·표·막대차트·선차트(추세)·도넛(구성비)·플로우·한줄강조·단계(steps: key/bad/ok)·코드블록·공식강조·용어각주(gloss)·용어집(terms)·**스키마카드(schema)**·**데이터흐름(dataflow)**·**레코드변화(table.diff)**·**비교매트릭스(table.matrix)**·**계층구조(layers)**·**쉬운말풀이(plain)**.

## 2. 슬라이드 한 장 원칙

| 규칙 | 내용 | 근거 |
|------|------|------|
| 헤드라인 = 완결 주장문 | 주제 라벨 금지. "매출이 40% 늘었어요"(O) / "3분기 매출"(X). **해요체 문장형** | Alley, 토스 UX writing |
| **헤드라인에 대상 이름 필수** | 무엇에 대한 이야기인지 **기술·제품·대상 이름을 헤드라인 안에** 넣는다. 제목만 읽어도 주제가 잡혀야 한다 | rp-deck |
| 한 장 = 한 메시지 | 주장 2개 이상이면 장을 나눔 | Duarte |
| 근거는 시각적으로 | 본문은 불릿 나열보다 차트·카드·다이어그램 | Alley |
| 3초 글랜스 테스트 | 3초 안에 요점이 잡히게 | Duarte/Reynolds |
| 여백 활용 | 핵심 하나를 여백으로 고립시켜 강조 | Reynolds |
| 시각 위계 | 장마다 지배 요소 1개, 크기·굵기·색·위치로 순위 | CLT |
| 일관성 | 그리드·타입스케일·색 역할을 전 장 고정 | CLT |

## 3. 데이터 시각화

**주제별 컴포넌트 선택은 [`visual-patterns.md`](visual-patterns.md)가 SSOT** — 스키마·데이터흐름·값 변화·기술 비교·계층 구조·추세·구성비를 무엇으로 그릴지 그 문서에서 고른다.

| 규칙 | 내용 | 근거 |
|------|------|------|
| 그림 우선 | 구조·흐름·변화·비교·수치는 문장 나열이 아니라 컴포넌트로 그린다 | Alley |
| **텍스트 3연장 금지** | 그림 없는 슬라이드가 **연속 3장**을 넘지 않는다. 넘으면 그 구간을 다시 설계 | rp-deck |
| **표로 쓸 수 있으면 표로** | 항목이 둘 이상 비교되면 문장 대신 `table`. "A는 ~하고 B는 ~해요" 문장이 나오려 하면 그 자리에서 표로 바꾼다 | rp-deck |
| **수치 2개 이상이면 차트** | 비교 가능한 실측치가 2개 이상이면 `.bars`, 시간 흐름이면 `.linechart`, 구성비면 `.donut`. 수치를 문장 안에 흘려보내지 않는다 | rp-deck |
| **수치가 없으면 공식으로** | 실데이터가 없어도 계산으로 유도되는 값은 `.formula` 한 줄로 보여준다. 가정은 각주에 명시 | rp-deck |
| data-ink 최대화 | 그리드·테두리·3D·그림자·불필요한 색 제거. 장식 배경·질감 금지 | Tufte |
| 직접 라벨 | 범례 대신 막대·선·범례 항목에 값 직접 표기 | UC Berkeley |
| 개수 제한 | 시리즈 ≤5~6, 색 ≤6, 도넛 ≤5, KPI 한 화면 ≤3(권장)~5 | 시각화 가이드 |
| 차트 1개 = 메시지 1개 | 그 장의 헤드라인만 증명 | Tufte |
| 정직한 축 | 막대는 0 기준선, 비율 왜곡 금지 | Tufte |
| 실데이터만 | 값이 없으면 차트 대신 카드·문장. 예시값이면 각주 명시 | rp-deck |
| 구체값으로 | 다이어그램에 추상 라벨(`데이터`,`요청`) 대신 실제 컬럼명·값·JSON 조각을 넣는다 | rp-deck |
| 시각+텍스트 병기 | 시각 요소는 설명을 대체하지 않음. 옆/아래에 해석·수치·용어를 함께 둠 | Mayer 멀티미디어 |

## 4. 인지 부하 감축

- 중복 효과 회피: 발표 스크립트 전문을 슬라이드에 그대로 넣지 않음 (Mayer)
- 청킹: 한 개념 = 한 단위로 쪼갬 (Mayer segmenting)
- 점진 공개: 복잡한 내용은 장을 나눠 단계로 (progressive disclosure)
- 신호화: 중요한 곳만 색·굵기로 큐, 장식 제거 (Mayer signaling)
- 근접성: 라벨은 대상 옆에 (split attention 회피)

## 5. 수치 가이드 (생성 시 강제)

| 항목 | 값 |
|------|-----|
| 헤드라인 | 완결 문장 1개 + **대상 이름 포함**, ≤~24자 권장 (이름을 넣느라 길어지는 건 허용) |
| 불릿 (쓸 경우) | 장당 ≤6개, 항목당 짧게 (6×6은 상한 heuristic) |
| 본문 최소 크기 | 18px+ (template 스케일 준수) |
| 대비 | 일반 텍스트 ≥4.5:1, 큰 텍스트 ≥3:1 (WCAG AA) |
| 폰트 | Pretendard 등 산세리프, 400/600/700만 사용 |
| KPI 카드 | 한 화면 ≤3 |
| 차트 시리즈/색 | ≤6 |

## 6. 토스 톤 & UX writing (본문 카피)

출처: Apps-in-Toss UX writing, toss.tech 8원칙.

| 규칙 | Don't → Do |
|------|-----------|
| 해요체 통일 | 모든 문장 해요체 |
| 문장형 > 명사형 | "송금 완료" → "송금했어요" |
| 능동형 > 수동형 | "됐어요" → "했어요" |
| 긍정형 > 부정형 | "이자 혜택 없음" → "이자를 더 받을 수 있어요" |
| 캐주얼 경어 | "확인하시겠어요?" → "확인할래요?" |
| 잡초 제거 | "앞으로 OOO을 하세요" → "OOO을 하세요" |
| 빈 문장 제거 | 제목을 본문에서 반복하지 않음 |
| 핵심만 | 이미 아는 정보는 생략 |
| 보편 단어 | 슬랭·밈·전문용어 금지 |

**주의**: 헤드라인은 "완결 주장문(해요체)". 명사 라벨("개요","결과")과 명사형 종결("송금 완료") 모두 금지.

**대상 이름 규칙 (§2 보강)** — 제목만 보고 무슨 이야기인지 알게 한다.

| Don't (주어가 없음) | Do (대상 이름을 넣음) |
|------|------|
| 응답이 40% 빨라졌어요 | Redis 캐시를 거치니 응답이 40% 빨라졌어요 |
| 구조를 개선했어요 | 주문 API를 큐 방식으로 바꿨어요 |
| Redis와 Kafka 비교 *(명사 라벨)* | Redis와 Kafka는 어울리는 자리가 달라요 |
| 이렇게 저장돼요 | 주문 테이블은 이런 칸들로 이뤄져 있어요 |

대명사·추상어("이것", "성능", "구조")만으로 끝내지 않는다. 수치가 있으면 대상 이름과 함께 넣는다.

## 7. 색 사용 규칙

- 인터랙션/강조: `--toss-blue`(#3182F6). 브랜드 블루(#0064FF)는 로고 등 브랜드 순간에만.
- 텍스트: 헤드라인 `--grey-900`, 본문 `--grey-700`, 캡션 `--grey-600`.
- 배경: 카드 white/`--grey-50`, 구분 `--grey-200` 헤어라인.
- 의미색만: 상승/긍정 `--positive`, 하락/부정 `--negative`. 색은 장식이 아니라 의미.
- 플랫 + 헤어라인 우선, 그림자는 실제 elevation에만 절제해 사용.

## 8. 용어 각주 (glossary)

독자가 뜻을 따로 찾지 않도록, 낯선 용어를 그 용어가 처음 나온 슬라이드 하단에 작게 설명한다. 기준 독자는 §0 — 개발자가 아니어도 읽힌다.

| 규칙 | 내용 |
|------|------|
| 위치 | 용어가 처음 등장한 슬라이드 하단 (`.gloss`). **`.gloss`를 쓰는 `<section>`에 `has-gloss` 클래스**를 함께 붙여 본문과 겹치지 않게 한다 |
| 선정 | 비전공 독자에게 낯선 말은 **전부 설명**. 슬라이드당 **2~5개**가 보통이고, 필요하면 더 넣는다 |
| 약어 | 풀텍스트 병기 — `TTL(Time To Live): 자동 만료 시간` |
| 형식 | ` · `로 구분, 용어는 `<b>`, 뜻은 회색. 예: `쿼럼: 과반 정족수(N/2+1) · TTL(Time To Live): 자동 만료 시간` |
| 분량 | 뜻은 한 구절로 압축. **최대 4줄**까지 허용(넘으면 일부를 끝 용어집으로 이관) |
| **재설명이 기본** | 어려운 용어는 **앞에서 설명했더라도 다시 나온 장에서 또 푼다**. 장 사이 거리와 무관하다. 독자는 그 장부터 볼 수도 있고, 앞장을 되짚게 만들지 않는다 |
| 중복을 아끼지 않는다 | 같은 뜻풀이가 여러 장에 반복돼도 괜찮다. 각주는 절대 위치라 본문을 밀지 않으므로 비용이 거의 없다 |
| 개념은 각주 말고 본문 | 한 줄로 안 끝나는 개념은 각주 대신 `.plain`(쉬운 말 풀이)이나 소개 슬라이드로 올린다 |
| **끝 용어집** | 용어가 많은(대략 8개+) 기술 덱은 **마무리 직전에 "용어 사전" 슬라이드**를 둔다 — 본문에 나온 핵심 용어를 `.terms`로 모아 한눈에 |
| 생략 | 낯선 용어가 없으면 각주·용어집을 넣지 않는다 |

마크업은 [`template.html`](template.html)의 `.gloss`(하단 각주)·`.terms`(용어집 슬라이드) 참조.

## 9. 깊이와 분량 (얼마나 담을까)

전달력을 위해 줄이되, **이해에 필요한 내용까지 잘라내지 않는다.** 과도한 압축은 오히려 이해를 막는다.

| 규칙 | 내용 |
|------|------|
| 복잡도에 맞춰 | 슬라이드 수를 주제 난이도·분량에 맞게 늘린다. 얕은 주제는 적게, 깊은 주제는 충분히 |
| **개요 + 심화 2단** | 복잡한 메커니즘은 **개요 흐름 한 장(전체 그림) → 심화 여러 장(단계별 상세)**으로 항상 나눠 보여준다. 개요만 두고 끝내지 않는다 |
| **중간 단계 생략 금지** | 흐름을 "A → Z"로 뭉치지 말고 거쳐가는 **중간 컴포넌트·단계를 모두 드러낸다**(예: 인그레스 → 라우팅 → 서비스 디스커버리 → 엔드포인트 → 파드). 뭉뚱그린 화살표 하나로 넘기지 않는다 |
| 메커니즘은 단계로 | 동작·실패 과정은 `.steps`로 분해. 위험 단계는 `bad`(빨강), 해소 단계는 `ok`(초록), 핵심은 `key`(파랑) |
| 근거·수치·예시 | 주장에 근거·구체 수치·코드·시나리오를 붙여 납득시킨다 |
| 심화는 나눠서 | 한 장이 넘치면 개념→상세→시나리오로 장을 쪼갠다 (progressive disclosure) |
| 흔한 오해·엣지 | 자주 틀리는 지점·예외를 별도 장으로 짚는다 |
| 과소·과대 모두 지양 | 뻔한 내용으로 장 수만 늘리지 않는다. 각 장은 새 정보를 담는다 |
| **임의 상한 금지** | 20·25장 같은 숫자로 미리 자르지 않는다. 복잡한 주제는 30~35장+도 자연스럽다. 처음부터 복잡도에 맞춰 넉넉히 설계하고, 얇게 잡았다가 늘리지 않는다 |
| **낯선 도구 먼저 소개** | 처음 나오는 핵심 도구·서비스(예: Sentry)는 코드·설정으로 **쓰기 전에** "무엇인지·왜 쓰는지" 소개 장을 먼저 둔다. 각주만으로 대체하면 갑자기 튀어나와 어색해진다 |

핵심: "한 장 = 한 메시지"는 각 장을 얇게 만들라는 뜻이 아니라, 한 장이 한 가지를 **깊이** 다루라는 뜻.

## 10. 생성 전 자가 린트 (anti-pattern 체크)

- [ ] 텍스트 벽(문단/불릿>6/스크립트 전문) 없음
- [ ] 주제 라벨 헤드라인 없음 (전부 완결 주장문)
- [ ] 한 장에 메시지 2개 이상 없음
- [ ] 차트 정크(3D·그림자·그리드·의미없는 색) 없음
- [ ] 범례 의존 없음 (직접 라벨)
- [ ] 축 왜곡 없음 (막대 0 기준)
- [ ] 위계·타입스케일 장간 일관
- [ ] 대비 4.5:1 이상, 본문 18px 이상
- [ ] 예시 데이터에 각주, 실데이터 아니면 차트 남용 안 함
- [ ] 시각 요소 옆에 해석·수치·용어 텍스트 병기 — 시각화가 설명을 대체하지 않음
- [ ] 카피 전부 해요체·문장형·긍정형
- [ ] **헤드라인마다 대상(기술·제품·대상) 이름이 들어 있음 — 제목만 보고 주제가 잡힘**(§2)
- [ ] **그림 없는 슬라이드가 연속 3장을 넘지 않음**(§3)
- [ ] **스키마·데이터흐름·값 변화·기술 비교·계층 구조·추세·구성비를 전용 컴포넌트로 그림**([`visual-patterns.md`](visual-patterns.md) §2)
- [ ] **다이어그램에 추상 라벨 대신 실제 컬럼명·값·데이터 조각이 들어 있음**(§3)
- [ ] **비전공 독자가 멈칫할 지점이 없음 — 용어는 첫 등장 자리에서 풀고, 어려운 개념엔 쉬운 말 풀이(`.plain`)를 붙임**(§0·§8)
- [ ] **"왜 필요한지" 장이 동작·구조 설명보다 앞에 있음**(§0)
- [ ] **`.gloss`를 쓴 `<section>`에 `has-gloss` 클래스가 붙어 있음**(§8)
- [ ] 낯선 용어에 하단 각주(§8), 약어는 풀텍스트 병기, 각주 네 줄 이내
- [ ] 이해에 필요한 근거·수치·예시가 충분함(과도 압축 아님), 복잡한 메커니즘은 단계로 분해(§9)
- [ ] 복잡한 흐름은 개요 1장 + 심화 여러 장, 중간 컴포넌트·단계를 생략하지 않음(§9)
- [ ] 낯선 용어를 넉넉히 각주로 풀고, 용어 많은 덱은 끝에 용어집 슬라이드 포함(§8)
- [ ] 뻔한 내용으로 장 수만 늘리지 않음 — 각 장이 새 정보를 담음(§9)
- [ ] 슬라이드 수를 임의 상한(20·25장 등)으로 자르지 않고 복잡도에 맞게 확장(§9)
- [ ] 처음 등장하는 핵심 도구·서비스는 사용 전에 소개 장이 있음 — 각주만으로 대체하지 않음(§9)
- [ ] 개요 다이어그램이 본문의 모든 소스·목적지·경로를 누락 없이 담음(§9)
- [ ] **비교·수치를 문장이 아니라 표·차트·공식으로 옮김**(§3)
- [ ] **어려운 용어는 앞에서 설명했더라도 다시 나온 장에서 또 풀어줌**(§8)
- [ ] **코드 예제가 그대로 복사해 컴파일·실행되는 형태임 — 줄인 부분이 있으면 `.cmt`에 명시**(§11)
- [ ] **캡션·헤드라인이 주장하는 동작이 그 장의 코드·그림에 실제로 보임**(§11)
- [ ] **앞 장의 판정과 뒤 장의 해법이 서로 모순되지 않음**(§11)
- [ ] **"항상·무조건·~만" 같은 단정 앞에 반례를 확인함**(§11)
- [ ] **인용한 사례에 출처와 결말이 함께 적혀 있음**(§11)
- [ ] **전 슬라이드가 1280×720 안에 들어감 — 높이 예산으로 더해보거나 실제로 렌더해 확인**([`visual-patterns.md`](visual-patterns.md) §7)
- [ ] **손으로 그린 인라인 SVG의 모든 블록이 x=0에서 시작함 — 라벨 열이 있는 막대·리스트도 라벨을 x=0에 둠**([`visual-patterns.md`](visual-patterns.md) §8)
- [ ] **인접 `<text>`의 y 간격이 글자 크기 + 8 이상이고, 어떤 요소도 viewBox 밖으로 나가지 않음**([`visual-patterns.md`](visual-patterns.md) §8)
- [ ] **`lint_svg.py`를 돌려 OVERLAP·CLIP 0건**(INDENT는 판단 후 채택·보류, [`visual-patterns.md`](visual-patterns.md) §8)

## 11. 코드·사례·주장의 정합성

장표의 코드는 읽히는 데서 끝나지 않고 **복사돼 쓰인다.** 그리고 캡션은 **그 장의 코드·그림이 실제로 하는 일만** 말해야 한다.

| 규칙 | 내용 |
|------|------|
| **복붙 가능한 코드** | 생성자·필드·import가 빠져 그대로는 컴파일되지 않는 예제를 싣지 않는다. 지면 때문에 줄여야 하면 `.cmt`에 무엇을 줄였는지 적는다 |
| **캡션은 코드가 하는 일만** | 캡션·헤드라인이 주장하는 동작이 그 장 코드에 **눈으로 보여야** 한다. 코드는 지연 로딩인데 캡션이 "부팅 때 실패해요"라고 쓰면 그 한 장이 덱 전체의 신뢰를 깎는다 |
| **앞뒤 판정 충돌 금지** | 앞 장 매트릭스에서 "못 잡아요"로 판정한 것을 뒤 장에서 해법으로 내놓지 않는다. 판정 표는 덱을 다 쓴 뒤 한 번 더 훑는다 |
| **단정 앞에 반례 확인** | "항상·무조건·~만·손해만" 같은 단정은 반례를 한 번 찾아본 뒤에 쓴다. 반례가 있으면 조건을 붙인다 |
| **사례엔 출처와 결말** | 남의 이슈·사고를 인용하면 번호·버전과 **결말**(머지됐는지, 어떻게 끝났는지)까지 적는다. 결말이 논지를 뒤집거나 오히려 뒷받침하기도 한다 |
| **예시 값은 예시라고** | 실 스키마·실측치가 아닌 값은 `.slide-note`에 "예시"라고 밝힌다 |
