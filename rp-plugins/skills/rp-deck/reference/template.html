구간 비교

DB 타임아웃 구간을 한 시간축에 겹쳐봐요

쉽게 말하면 러시아 인형처럼 안쪽 상자가 바깥 상자보다 작아야 해요. 안쪽이 더 크면 바깥 상자 뚜껑이 안 닫혀요.
타임아웃(timeout): 여기까지만 기다리고 끊겠다고 정해 둔 시간 · connectionTimeout: 커넥션 풀에서 커넥션을 받기까지 기다리는 한도 · socketTimeout: 요청을 보낸 뒤 응답 한 조각을 기다리는 한도 · 트랜잭션(transaction): 여러 쿼리를 "다 되거나 다 안 되거나"로 묶는 단위

데이터 저장 방식

주문 테이블은 이런 칸들로 이뤄져 있어요

orders컬럼 5개
PKidBIGINT주문마다 붙는 고유 번호예요
FKuser_idBIGINT누가 주문했는지 회원 표를 가리켜요
statusVARCHAR(20)결제 전인지 후인지 상태를 담아요
amountDECIMAL(12,2)결제 금액이에요. 소수점까지 정확히 담아요
IDXcreated_atTIMESTAMP주문한 시각이에요. 최근 순 조회에 자주 써서 색인을 걸어요
쉽게 말하면 엑셀 시트의 첫 줄(제목 줄)을 정해두는 일이에요. 어떤 칸을 만들지 미리 약속해두는 거예요.
컬럼: 표의 세로 칸, 엑셀의 열 · PK(Primary Key): 행을 하나로 특정하는 대표 번호 · FK(Foreign Key): 다른 표의 행을 가리키는 연결 고리 · IDX(Index): 자주 찾는 값을 빨리 찾게 만든 색인, 책 맨 뒤 찾아보기와 같아요

값의 변화

결제가 끝나면 주문 한 줄에서 두 칸이 바뀌어요

시점statuspaid_atamount
결제 전PENDINGNULL12000.00
결제 후PAID2026-07-27 07:0012000.00

줄을 새로 만들지 않고 같은 줄의 값만 고쳐요. 그래서 주문 번호는 그대로예요.

레코드: 표의 가로 한 줄, 주문 하나 · NULL: 아직 값이 없다는 표시(0이나 빈 글자와 다름) · PENDING: 결제를 기다리는 중이라는 상태값
기술 비교

Redis와 Kafka는 어울리는 자리가 서로 달라요

이런 상황이라면RedisKafka
같은 값을 아주 빨리 다시 꺼내기잘 맞아요안 맞아요
주문이 한꺼번에 몰릴 때 줄 세우기버거워요잘 맞아요
지난 기록을 다시 돌려 읽기어려워요잘 맞아요
쉽게 말하면 Redis는 자주 쓰는 물건을 올려두는 책상이고, Kafka는 물건이 순서대로 흘러가는 컨베이어 벨트예요.
Redis: 데이터를 메모리에 두고 아주 빠르게 읽고 쓰는 저장소 · Kafka: 이벤트를 순서대로 쌓아두고 여러 곳이 나눠 읽는 메시지 플랫폼 · 메모리: 전원이 꺼지면 사라지지만 디스크보다 훨씬 빠른 저장 공간
전체 구조

서비스는 화면부터 DB까지 네 층으로 쌓여 있어요

화면(프론트)
사용자가 직접 보고 누르는 곳이에요.
API 서버
누른 결과를 받아 규칙에 맞는지 확인하고 처리해요.
캐시
자주 찾는 값을 미리 꺼내 두고 DB 대신 답해요.
데이터베이스
최종 기록을 오래 안전하게 보관해요.
프론트(frontend): 사용자 눈에 보이는 화면 영역 · API(Application Programming Interface): 화면과 서버가 주고받기로 정한 약속 · 캐시(cache): 자주 쓰는 값을 잠깐 복사해 두는 임시 보관함 · 데이터베이스(DB): 데이터를 표 형태로 오래 보관하는 창고
