# rp-deck 시각 표현 패턴 (주제 → 그림 매핑 SSOT)

"글로 설명하려는 순간"이 곧 "그림으로 바꿀 지점"이다. 이 문서는 **어떤 주제를 어떤 컴포넌트로 그릴지**를 정한다.
마크업·CSS는 [`template.html`](template.html)이 SSOT. 구조·톤 규칙은 [`design-rules.md`](design-rules.md).

## 1. 원칙

| 규칙 | 내용 |
|------|------|
| 그림 우선 | 구조·흐름·변화·비교·수치는 문장 나열 대신 컴포넌트로 그린다 |
| 병기 필수 | 그림은 텍스트를 대체하지 않는다. 해석 문장·수치·용어 각주를 함께 둔다 |
| 구체값으로 | 추상 라벨(`데이터`, `요청`) 대신 실제 컬럼명·값·JSON 조각을 넣는다 |
| 중간 생략 금지 | 흐름은 거쳐가는 홉을 전부 그린다. A→Z 한 화살표 금지 |
| 밀도 게이트 | 텍스트만 있는 슬라이드가 **연속 3장** 넘지 않는다. 넘으면 그 구간을 그림으로 다시 설계 |
| 720px 한계 | 한 장은 1280×720에 들어가야 한다. 넘치면 내용을 눌러 담지 말고 **장을 나눈다**. 템플릿이 `.slide>*{flex:none}`이라 넘치면 눌리지 않고 그대로 삐져나와 눈에 띈다 |

## 2. 주제 → 컴포넌트 매핑

| 이런 걸 설명한다면 | 이 컴포넌트로 | 반드시 함께 |
|------|------|------|
| 데이터를 어디에 어떤 칸으로 저장하는지 | `.schema` (스키마 카드) | 컬럼별 **쉬운 설명** 한 줄, 키 뱃지(PK/FK/IDX) |
| 데이터가 어디를 거쳐 흘러가는지 | `.dataflow` (홉별 데이터 모양) | 각 홉의 **실제 데이터 조각** + 그 홉이 하는 일 |
| 값이 전/후로 어떻게 바뀌는지 | `table.diff` (레코드 변화) | 바뀐 셀만 `.chg` 강조, 안 바뀐 칸도 같이 보여줌 |
| 기술 A와 B 중 뭘 쓸지 | `table.matrix` (비교 매트릭스) | 행은 **상황**, 셀은 `yes/mid/no` + 이유 한마디 |
| 시스템이 몇 겹으로 쌓였는지 | `.layers` (계층 구조) | 층마다 "여기서 무슨 일이 일어나요" 한 줄 |
| 동작·실패가 어떤 순서로 일어나는지 | `.steps` (단계) | 위험=`bad`, 해소=`ok`, 핵심=`key` |
| 컴포넌트 사이 관계·경로 | `.flow` (플로우) | 노드 이름은 실제 서비스·모듈명 |
| 시간에 따른 증감 | `.linechart` (선) | 점 위 값 직접 라벨 + 해석 문장 |
| 전체 중 비중 | `.donut` (도넛, ≤5조각) | 범례에 값 직접 표기 |
| 항목 간 크기 비교·랭킹 | `.bars` (막대) | 0 기준선, 막대 끝 값 표기 |
| 단일 핵심 지표 | `.kpi` (큰 숫자, ≤3) | 비교 기준(전 대비 등) |
| 항목별 속성 나열 | `table` (표) | 열 3~5개, 첫 열은 항목명 |
| 명령·설정·코드 | `.code` | 줄 아래 `.cmt`로 **한국어 해설** |
| 계산식·공식 | `.formula` | 기호마다 무슨 뜻인지 각주 |
| 어려운 개념을 방금 말했을 때 | `.plain` (쉬운 말 풀이) | 일상 비유 한 문장 |

## 3. 컴포넌트 사용 규칙

### `.schema` — 스키마 카드
- 헤더에 테이블명(mono) + 컬럼 개수. 행마다 `키 뱃지 / 컬럼명 / 타입 / 설명`.
- **설명 칸은 타입 반복이 아니라 "이 칸이 왜 있는지"**. `BIGINT` → "주문마다 붙는 고유 번호예요".
- 컬럼 8개를 넘으면 핵심 컬럼만 두고 "그 외 N개" 행으로 접거나 장을 나눈다.
- PK·FK·인덱스는 뱃지로만 표시하고 뜻은 하단 `.gloss`에서 푼다.

### `.dataflow` — 데이터 흐름
- 홉 3~5개. 홉마다 `제목 / 그 시점의 데이터(mono) / 하는 일 한 줄`.
- **데이터 칸이 비면 이 컴포넌트를 쓰지 않는다** — 그럴 땐 `.flow`로.
- 강조할 홉 하나만 `.hi`.

### `table.diff` — 레코드 변화
- 첫 열은 시점 라벨("결제 전"/"결제 후"), 나머지 열은 컬럼.
- 바뀐 셀만 `.chg`. **안 바뀐 컬럼도 남겨야** 무엇이 안 변했는지 보인다.
- 행 추가/삭제를 보여줄 땐 시점 라벨에 "새 줄 생김"/"줄 사라짐"을 적는다.

### `table.matrix` — 비교 매트릭스
- 행 = 사용자가 처한 **상황**(기능 이름이 아니라). "주문이 몰릴 때 줄 세우기".
- 셀은 판정어(`잘 맞아요`/`버거워요`/`안 맞아요`) — 기호(○×)만 두지 않는다.
- 열 2~3개. 4개 넘으면 표로 바꾼다.

### `.layers` — 계층 구조
- 위에서 아래로 사용자와 가까운 순. 층 3~5개.
- 층 이름은 200px 고정 폭이므로 8자 내외.

### `.plain` — 쉬운 말 풀이
- 전문 설명 **바로 아래**에 둔다. 한 슬라이드에 하나만.
- 형식: `쉽게 말하면 + 일상 비유 한 문장`. 비유는 사무실·가게·책·줄서기 등 누구나 아는 것으로.
- 비유가 억지스러우면 넣지 않는다. 틀린 비유가 없는 것보다 나쁘다.

## 4. 골든 패턴 — "데이터 저장 방식"을 설명할 때

한 장으로 뭉치지 않고 **3장 세트**로 나눈다.

| 장 | 컴포넌트 | 담는 내용 |
|----|----------|-----------|
| 1 | `.schema` + `.plain` + `.gloss` | 어떤 칸이 있고 각 칸이 왜 필요한지 |
| 2 | `.dataflow` | 그 데이터가 화면에서 DB까지 어떤 모양으로 흘러가는지 |
| 3 | `table.diff` | 사건(결제·취소 등)이 일어나면 어떤 값이 바뀌는지 |

필요하면 앞에 `.layers`(전체 구조), 뒤에 `.steps`(실패했을 때)를 더 붙인다.

## 5. 골든 패턴 — "기술 A vs B"를 설명할 때

| 장 | 컴포넌트 | 담는 내용 |
|----|----------|-----------|
| 1 | `.card-row` 또는 `.plain` | A는 무엇인지, B는 무엇인지 각각 한 줄 소개 |
| 2 | `table.matrix` | 상황별로 어느 쪽이 맞는지 |
| 3 | `.dataflow` ×2 또는 `.two-col` | 같은 요청이 A와 B에서 각각 어떻게 처리되는지 |
| 4 | `.bars` 또는 `table` | 수치가 있으면 비교, 없으면 특성 표 |

## 6. 금지

- 라이브러리·이미지 파일 사용 금지. 순수 CSS/SVG만.
- `template.html`의 CSS 변수·클래스를 임의 변경 금지. 새 표현은 기존 컴포넌트 조합으로.
- 실데이터 없이 차트 만들기 금지. 예시값이면 `.slide-note`에 각주.
- 그림을 넣었다고 설명 문장·용어 각주를 줄이는 것 금지.
