# rp-deck 시각 표현 패턴 (주제 → 그림 매핑 SSOT)

"글로 설명하려는 순간"이 곧 "그림으로 바꿀 지점"이다. 이 문서는 **어떤 주제를 어떤 컴포넌트로 그릴지**를 정한다.
마크업·CSS는 [`template.html`](template.html)이 SSOT. 구조·톤 규칙은 [`design-rules.md`](design-rules.md).

## 1. 원칙

| 규칙 | 내용 |
|------|------|
| 그림 우선 | 구조·흐름·변화·비교·수치는 문장 나열 대신 컴포넌트로 그린다 |
| 병기 필수 | 그림은 텍스트를 대체하지 않는다. 해석 문장·수치·용어 각주를 함께 둔다 |
| 구체값으로 | 추상 라벨(`데이터`, `요청`) 대신 실제 컬럼명·값·JSON 조각을 넣는다 |
| 중간 생략 금지 | 흐름은 거쳐가는 홉을 전부 그린다. A→Z 한 화살표 금지 |
| 밀도 게이트 | 텍스트만 있는 슬라이드가 **연속 3장** 넘지 않는다. 넘으면 그 구간을 그림으로 다시 설계 |
| 720px 한계 | 한 장은 1280×720에 들어가야 한다. 넘치면 내용을 눌러 담지 말고 **장을 나눈다**. 템플릿이 `.slide>*{flex:none}`이라 넘치면 눌리지 않고 그대로 삐져나온다. 설계할 때 더해보는 예산은 §7 |

## 2. 주제 → 컴포넌트 매핑

| 이런 걸 설명한다면 | 이 컴포넌트로 | 반드시 함께 |
|------|------|------|
| 데이터를 어디에 어떤 칸으로 저장하는지 | `.schema` (스키마 카드) | 컬럼별 **쉬운 설명** 한 줄, 키 뱃지(PK/FK/IDX) |
| 데이터가 어디를 거쳐 흘러가는지 | `.dataflow` (홉별 데이터 모양) | 각 홉의 **실제 데이터 조각** + 그 홉이 하는 일 |
| 값이 전/후로 어떻게 바뀌는지 | `table.diff` (레코드 변화) | 바뀐 셀만 `.chg` 강조, 안 바뀐 칸도 같이 보여줌 |
| 기술 A와 B 중 뭘 쓸지 | `table.matrix` (비교 매트릭스) | 행은 **상황**, 셀은 `yes/mid/no` + 이유 한마디 |
| 시스템이 몇 겹으로 쌓였는지 | `.layers` (계층 구조) | 층마다 "여기서 무슨 일이 일어나요" 한 줄 |
| 동작·실패가 어떤 순서로 일어나는지 | `.steps` (단계) | 위험=`bad`, 해소=`ok`, 핵심=`key` |
| 컴포넌트 사이 관계·경로 | `.flow` (플로우) | 노드 이름은 실제 서비스·모듈명 |
| 서버·DB·캐시·큐가 **어떻게 배치되고 무엇으로 연결되는지**, 어디까지가 우리 시스템인지 | `.sysmap` (시스템 구성도) | 경계 안팎 구분 + 노드마다 타입 라벨 + 연결선마다 무슨 연결인지 |
| 여러 구간이 **언제 시작해 어디까지인지**·서로 품는지 (타임아웃·SLA·재시도·배포 윈도우·단계별 소요) | `.timeline` (타임라인 구간) | 공통 시간축 + 구간마다 길이 값, 시작점이 갈리는 곳엔 기준선 |
| 시간에 따른 증감 | `.linechart` (선) | 점 위 값 직접 라벨 + 해석 문장 |
| 전체 중 비중 | `.donut` (도넛, ≤5조각) | 범례에 값 직접 표기 |
| 항목 간 크기 비교·랭킹 | `.bars` (막대) | 0 기준선, 막대 끝 값 표기 |
| 단일 핵심 지표 | `.kpi` (큰 숫자, ≤3) | 비교 기준(전 대비 등) |
| 항목별 속성 나열 | `table` (표) | 열 3~5개, 첫 열은 항목명 |
| 명령·설정·코드 | `.code` | 줄 아래 `.cmt`로 **한국어 해설** |
| 계산식·공식 | `.formula` | 기호마다 무슨 뜻인지 각주 |
| 어려운 개념을 방금 말했을 때 | `.plain` (쉬운 말 풀이) | 일상 비유 한 문장 |

## 3. 컴포넌트 사용 규칙

### `.schema` — 스키마 카드
- 헤더에 테이블명(mono) + 컬럼 개수. 행마다 `키 뱃지 / 컬럼명 / 타입 / 설명`.
- **설명 칸은 타입 반복이 아니라 "이 칸이 왜 있는지"**. `BIGINT` → "주문마다 붙는 고유 번호예요".
- 컬럼 8개를 넘으면 핵심 컬럼만 두고 "그 외 N개" 행으로 접거나 장을 나눈다.
- PK·FK·인덱스는 뱃지로만 표시하고 뜻은 하단 `.gloss`에서 푼다.

### `.dataflow` — 데이터 흐름
- 홉 3~5개. 홉마다 `제목 / 그 시점의 데이터(mono) / 하는 일 한 줄`.
- **데이터 칸이 비면 이 컴포넌트를 쓰지 않는다** — 그럴 땐 `.flow`로.
- 강조할 홉 하나만 `.hi`.

### `table.diff` — 레코드 변화
- 첫 열은 시점 라벨("결제 전"/"결제 후"), 나머지 열은 컬럼.
- 바뀐 셀만 `.chg`. **안 바뀐 컬럼도 남겨야** 무엇이 안 변했는지 보인다.
- 행 추가/삭제를 보여줄 땐 시점 라벨에 "새 줄 생김"/"줄 사라짐"을 적는다.

### `table.matrix` — 비교 매트릭스
- 행 = 사용자가 처한 **상황**(기능 이름이 아니라). "주문이 몰릴 때 줄 세우기".
- 셀은 판정어(`잘 맞아요`/`버거워요`/`안 맞아요`) — 기호(○×)만 두지 않는다.
- 열 2~3개. 4개 넘으면 표로 바꾼다.

### `.layers` — 계층 구조
- 위에서 아래로 사용자와 가까운 순. 층 3~5개.
- 층 이름은 200px 고정 폭이므로 8자 내외.

### `.timeline` — 타임라인 구간

**"A는 3초, B는 6초, C는 10초"처럼 시간·구간 값이 3개 이상 나열되면 그 자리에서 이걸로 그린다.** 막대(`.bars`)는 길이만 비교하지만, 타임라인은 **어디서 시작해 어디서 끝나는지**까지 보여줘서 포함·초과 관계가 눈에 보인다.

- **좌표 규칙 하나만 지킨다**: `x = 시작 시각`, `width = 길이`. 모든 행이 **같은 축**을 쓴다(행마다 축을 다시 잡지 않는다). 템플릿 데모는 `0초 = x280`, `1초 = 80px`.
- 행 4~7개. 위에서 아래로 **바깥(가장 큰) 구간 → 안쪽 구간** 순. 이 순서라야 "안쪽이 바깥보다 작아야 한다"가 계단 모양으로 보인다.
- 시작점이 갈리는 지점(커넥션 확보·요청 도착 등)엔 `.tl-mark` 점선 + 한 줄 라벨. 시작이 전부 같으면 생략한다.
- 색은 의미로만 고른다: `outer` 바깥 예산 · `wait` 대기 · 기본(파랑) 핵심 · `ghost` 묶는 구간(테두리) · `ok` 실측 · `bad` 초과. 장식으로 색을 늘리지 않는다.
- 값은 막대 **안에** 직접 쓴다(범례 금지). 밝은 막대(`outer`·`ghost`) 위 글자는 `.tl-val.on-light`·`.on-ghost`로 바꿔 대비를 지킨다.
- 하단에 시간축 눈금을 반드시 둔다. 눈금 없이 막대만 있으면 길이가 근거 없는 그림이 된다.
- **잘못된 설정을 보여줄 땐 같은 축에 한 장 더** — 올바른 배치 다음 장에 뒤집힌 배치를 `bad`로 그리면 무엇이 문제인지 비교로 잡힌다.

### `.sysmap` — 시스템 구성도

**"서버가 몇 개고 DB·Redis·큐가 어디에 붙는지"를 설명하려는 순간 이걸로 그린다.** `.flow`는 화살표로 이어진 경로만 보여주지만, 구성도는 **경계(어디까지가 우리 것인지)·타입(무엇인지)·연결 성격(동기냐 비동기냐)** 세 가지를 한 장에 담는다.

- **경계는 2겹까지**: 바깥 `.sm-zone`(우리가 운영하는 범위) + 안쪽 `.sm-group`(서브시스템 묶음) **3개 이하**. 리전·VPC까지 3겹으로 가지 않는다 — 안쪽 노드가 읽히지 않는다.
- **외부 시스템은 경계 밖에** `.sm-node.ext`(점선 테두리)로 둔다. 결제사·배송사처럼 **우리가 못 고치는 것**이 무엇인지가 구성도의 핵심 정보다.
- **노드 8종**: `CLIENT` / `GATEWAY` / `APP` / `DB` / `CACHE` / `QUEUE` / `STORAGE` / `EXTERNAL`. 타입은 **노드 안 작은 라벨**로 적고, 색은 역할 4개(진입점 `entry` · 우리 서비스 `app` · 상태 저장소 기본 · 외부 `ext`)만 쓴다. 8종을 8색으로 칠하지 않는다.
- **연결선마다 라벨 필수**: `주문 저장`·`재고 캐시 조회`처럼 **무슨 연결인지** 적는다. 화살표만 있으면 왜 이어졌는지 알 수 없다.
- **비동기는 점선**(`.sm-link.async`). 점선의 뜻은 **노드 이름이나 각주에서 풀어** 범례 없이 읽히게 한다(범례 의존 금지).
- **노드 10개 이하**. 넘으면 개요 한 장 + 서브시스템 상세 장으로 나눈다.
- ⛔ **포트·내부 호스트·내부 IP·인증서 경로를 적지 않는다.** 장표는 공개 게시판에 올라간다. 프로토콜(HTTP·gRPC)까지가 한계다.

### 흐름 계열 4종 — 언제 무엇을 쓰나

넷 다 상자와 화살표라 헷갈린다. **무엇을 묻는 장인지**로 고른다.

| 그 장의 질문 | 컴포넌트 |
|------|------|
| 이게 **어디에 배치되고 무엇과 연결**돼 있나 (서버·DB·캐시·외부 연동) | `.sysmap` |
| 데이터가 **각 홉에서 어떤 모양**으로 바뀌나 | `.dataflow` |
| 요청이 **어느 순서로 어디를 거치나** (배치·타입 구분 없이 경로만) | `.flow` |
| 시스템이 **몇 겹으로 쌓여** 있나 (위아래 계층) | `.layers` |

### `.plain` — 쉬운 말 풀이
- 전문 설명 **바로 아래**에 둔다. 한 슬라이드에 하나만.
- 형식: `쉽게 말하면 + 일상 비유 한 문장`. 비유는 사무실·가게·책·줄서기 등 누구나 아는 것으로.
- 비유가 억지스러우면 넣지 않는다. 틀린 비유가 없는 것보다 나쁘다.

## 4. 골든 패턴 — "데이터 저장 방식"을 설명할 때

한 장으로 뭉치지 않고 **3장 세트**로 나눈다.

| 장 | 컴포넌트 | 담는 내용 |
|----|----------|-----------|
| 1 | `.schema` + `.plain` + `.gloss` | 어떤 칸이 있고 각 칸이 왜 필요한지 |
| 2 | `.dataflow` | 그 데이터가 화면에서 DB까지 어떤 모양으로 흘러가는지 |
| 3 | `table.diff` | 사건(결제·취소 등)이 일어나면 어떤 값이 바뀌는지 |

필요하면 앞에 `.layers`(전체 구조), 뒤에 `.steps`(실패했을 때)를 더 붙인다.

## 5. 골든 패턴 — "기술 A vs B"를 설명할 때

| 장 | 컴포넌트 | 담는 내용 |
|----|----------|-----------|
| 1 | `.card-row` 또는 `.plain` | A는 무엇인지, B는 무엇인지 각각 한 줄 소개 |
| 2 | `table.matrix` | 상황별로 어느 쪽이 맞는지 |
| 3 | `.dataflow` ×2 또는 `.two-col` | 같은 요청이 A와 B에서 각각 어떻게 처리되는지 |
| 4 | `.bars` 또는 `table` | 수치가 있으면 비교, 없으면 특성 표 |

## 6. 금지

- 라이브러리·이미지 파일 사용 금지. 순수 CSS/SVG만.
- `template.html`의 CSS 변수·클래스를 임의 변경 금지. 새 표현은 기존 컴포넌트 조합으로.
- 실데이터 없이 차트 만들기 금지. 예시값이면 `.slide-note`에 각주.
- 그림을 넣었다고 설명 문장·용어 각주를 줄이는 것 금지.


## 7. 높이 예산 (1280×720 안에 넣기)

`.slide`는 `height:720px; overflow:hidden`에 세로 가운데 정렬이라, **넘치면 위아래가 잘리고 각주와 본문이 겹친다.** 다 만든 뒤에 발견하면 장을 통째로 다시 짜야 하므로 설계할 때 아래 예산으로 더해본다.

### 쓸 수 있는 본문 높이

| 슬라이드 | 위·아래 여백 | 본문 예산 |
|---|---|---|
| 각주 없음 (`.slide`) | 72 + 72 | **576px** |
| 각주 있음 (`.slide.has-gloss`) | 72 + 160 | **488px** |

`.gloss`는 `position:absolute`라 예산에 더하지 않는다. 대신 아래 여백이 160px로 이미 늘어나 있다.

### 요소별 대략 높이

Pretendard 기준 실측값이다. 별말 없으면 한 줄일 때의 높이이고 위 여백을 포함한다.

| 요소 | 높이 | 비고 |
|---|---|---|
| `.eyebrow` | 40 | 아래 여백 16 포함 |
| `.headline` | 57 | 두 줄이면 114 |
| `.subcopy` | 59 | 두 줄이면 94 |
| `.slide-note` | 55 | |
| `.plain` | 85 | 두 줄이면 114 |
| `table` | 40 + 51 + (행수 × 58~63) | 여백 + 헤더 + 행 |
| `.steps` | 32 + (단계수 × 44) | 두 줄짜리 단계는 60 |
| `.code` 블록 1개 | 30 + (줄수 × 29) + 36 | 블록 패딩 36, `.cmt`가 붙으면 +25 |
| `.card-row` | 44 + 200 | 카드 3개 |
| `.kpi-row` | 48 + 200 | |
| `.two-col` | 44 + 패널 높이 | 패널 = 패딩 64 + 태그 33 + 내용 |
| `.layers` | 32 + (층수 × 63) + (층수−1) × 12 | |
| `.dataflow` | 36 + 170 | 홉 4개 |
| `.flow` | 60 + 74 | |
| `.formula` | 44 + 172 | |
| `.timeline` | 24 + viewBox 높이 | 폭 1104에 맞춰 1:1 렌더. 행 n개면 viewBox 높이 ≈ 36n + 56 (행 간격 36, 축·눈금 56) |
| `.sysmap` | 24 + viewBox 높이 | 폭 1104에 맞춰 1:1 렌더. 노드 3행이면 viewBox 높이 ≈ 352 (행 높이 62 + 행 간격 58 + 경계 여백) |
| `.terms` | 32 + (행수 × 62) | 2열이라 행수 = 항목수 ÷ 2 |

### 자주 넘치는 조합

| 조합 | 결과 | 대응 |
|---|---|---|
| 코드 블록 2개 + 각주 | 거의 항상 초과 | 장을 둘로 나눈다 |
| 표 5행 + 부연 문장 + 각주 | 여유 20px 이하로 아슬아슬 | 행을 줄이거나 각주를 뺀다 |
| `.two-col` 안에 `.code` | 양쪽 패널이 **긴 쪽에 맞춰 늘어난다** | 두 코드의 줄 수를 맞추고 5줄 이내로 |
| 코드 한 줄이 패널 폭을 넘음 | 자동 줄바꿈으로 한 줄이 두 줄이 됨 | `.two-col` 안에서는 한 줄 47자 이내 |

### 검증

브라우저에서 1280×720으로 열어보면 잘린 장이 바로 눈에 띈다. 자동화한다면 각 `.slide`의 **직계 자식 높이 합 + 위아래 패딩**을 720과 비교한다. `position:absolute`인 자식(`.gloss`)은 빼고, `margin-top:auto`인 `.kicker`는 남는 공간을 흡수하므로 마무리 장이 720에 근접해 보여도 실제 초과가 아니다.

## 8. 손으로 그리는 인라인 SVG의 좌표 규칙

컴포넌트(`.steps`·`.layers` 등)는 CSS가 정렬해 주지만, **인라인 SVG는 레이아웃 엔진이 없다.** 좌표를 손으로 적으므로 어긋나도 렌더 오류가 나지 않고 그대로 배포된다. 아래 세 가지는 눈으로 놓치기 쉬우니 규칙으로 고정한다.

### 좌표계 = 본문 폭

`.slide`의 좌우 패딩이 88px이므로 본문 폭은 **1104px**이다. `viewBox="0 0 1104 H"` + `svg{width:100%}`로 두면 **SVG의 x=0이 헤드라인 왼쪽 끝과 1:1로 맞는다.** 다른 폭을 쓰면 환산이 필요해지므로 1104로 고정한다.

| 규칙 | 내용 |
|------|------|
| **블록 좌단 = x=0** | 블록의 **가장 왼쪽 끝**이 x=0에 오게 한다. 헤드라인·각주가 x=0에 붙어 있으므로, 안쪽에서 시작하는 블록은 **그 장에서만 붕 뜬 것처럼 보인다** |
| **라벨 열은 가장 긴 라벨이 x=0** | 라벨 열을 오른쪽 맞춤(`text-anchor="end"`)해도 된다 — 단 **가장 긴 라벨이 x=0에서 시작하도록** 앵커 x를 잡는다(`.timeline`이 이 방식). 라벨이 한두 글자면 앵커를 쓰지 말고 그냥 `x="0"` |
| ⛔ 흔한 실수 | 짧은 라벨을 넉넉한 앵커 x에 오른쪽 맞춤하면 **앵커와 실제 좌단이 크게 벌어진다.** 1글자 라벨을 `x="180" text-anchor="end"`로 두면 좌단이 164 — 164px이 이유 없이 빈다 |
| 들여쓰기는 계층만 | x>0에서 시작해도 되는 건 **종속·분기를 나타낼 때**뿐이다(플로우의 두 번째 홉, 결정 트리의 가지). 장식적 들여쓰기 금지 |
| **세로 간격 ≥ 글자 크기 + 8** | 인접 `<text>`의 `y` 차이. SVG는 자동 흐름이 없어 간격이 모자라면 **조용히 겹친 채** 렌더된다 |
| **박스는 품거나 떨어지거나** | 사각형끼리 **걸쳐 놓지 않는다.** 존이 노드를 완전히 품는 건 정상, 모서리만 겹치는 건 배치 실수다 |
| **viewBox 밖 금지** | 마지막 요소의 `y` + 글자 크기 × 0.25 ≤ viewBox 높이. SVG 루트는 `overflow:hidden`이라 넘친 만큼 잘린다 |

### 검증

[`scripts/lint_svg.py`](../scripts/lint_svg.py)가 텍스트 겹침(OVERLAP)·박스 겹침(NODE_OVERLAP)·잘림(CLIP)·왼쪽 여백 이탈(INDENT)을 기계로 잡는다. 지적이 있으면 종료 코드 1.

```
python3 <스킬경로>/scripts/lint_svg.py <덱 HTML 또는 디렉터리>
```

INDENT는 **반복 행 블록 옆 왼쪽 여백이 비었을 때만** 잡는다. 그리드의 오른쪽 열이나 플로우의 분기처럼 같은 y 구간에 x=0 요소가 있으면 지적하지 않는다. 산포도처럼 의도적으로 느슨한 배치는 걸릴 수 있으니, 지적은 **판단 대상이지 자동 수정 대상이 아니다.**
